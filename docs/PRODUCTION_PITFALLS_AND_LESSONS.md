## 一、赛道垂直度与商业定位防漂移铁律

### 1. 踩坑复盘
在与用户探讨选题时，曾出现过“未来就业风口”、“教别人租机器人这门生意怎么做”等探讨。这类选题虽然看似有当下热度，但严重偏离了账号核心受众画像，会导致账号定位稀释，沦为泛职场/副业加盟号。

### 2. 硬核教训与沉淀规则
- **绝对护城河**：本账号**100% 聚焦于【实体产业、大众消费供应链硬账、大宗商品咽喉、县域隐形冠军与泡沫出清】**。
- **一票否决门禁（Auto-Veto）**：
  - 严禁立项任何“泛职场就业指导”、“求职秘籍”、“副业赚钱”、“招商加盟培训”、“教你做某行业”等内容；
  - 严禁立项脱离真实供应链与成本账本的纯概念炒作、中介软文；
  - 选题雷达（`scripts/radar/topic_dedup.py`）中常态化配置 `BUREAUCRATIC_NOISE` 强力过滤词，从源头掐灭杂音。

## 二、配图历史索引覆盖查重陷阱（本地查重 vs 全库查重）

### 1. 踩坑复盘
在为《几万块的AI投料机，老渔民为什么换回了铁锹？》更换配图时，初次自查脚本仅比对了本地 `generated/` 目录下的 367 张图片，误以为汉明距离均大于 90。但在运行 `sync_hash_chain.py` 及 `pipeline.py check` 时，被底层硬阻断：
```
命中已发布配图：wx_33e06fea5a74737151662b82/body/2（距离 5），必须更换
```
**根因分析**：账号历史上已在微信正式发布、存档在后台历史数据库中的图片（共 233+ 张真实指纹）并不全在本地单一目录中！

### 2. 硬核教训与沉淀规则
- **唯一查重真理源**：图片查重须通过专用 CLI 核验其实际返回的历史索引与 coverage；底层接口为：
  ```python
  from tools.jackie_studio.engine.history import published_images
  historical, coverage = published_images()
  ```
- **先核覆盖再验距**：`scripts/screen_candidate_images.py` 使用 256 位 dHash16；coverage 必须为完整且一致的 ok，非 ok、不完整或空库均阻断导出。可用 `--ledger` 保存本次覆盖、指纹、距离和耗时；本地索引不冒称全号 live 覆盖。
- **先验距再落库**：
  1. 下载候选图片后，在执行 `copy` 或写入 `photos/` 之前，必须首先遍历 `published_images()` 计算 dHash 汉明距离；
  2. **双重硬门禁**：
     - **距历史已发库距离**：必须 `> 30`（仅报告本次索引相似度，不据此证明流量或降权因果）；
     - **篇内组内两两距离**：必须 `> 30`（严防一篇文章中多张配图构图相似，如多张同一角度的鱼塘水面）。

## 三、国内图片寻源防广告、防红章、防钓鱼版权与裁切与许可实战 SOP

### 1. 踩坑复盘
在打破仅依赖 Wikimedia、Pexels 等国外图库的限制、转向国内全网纪实寻源时，存在三大实战痛点：
1. **版权钓鱼碰瓷地雷**：商业图库（如视觉中国、图虫、全景网络、海洛创意等）通过全网爬虫进行商业维权，一旦不慎抓取其图源将引发法律风险；
2. **水印与边角戳记破坏美感**：国内新闻门户或政务纪实图往往在右下角或底部带有媒体台标、发布时间戳或水印；以往打马赛克或模糊处理极其粗劣，严重违反杂志级审美；
3. **低效爬虫与资源浪费**：启动重型无头浏览器截屏找图速度慢、内存占用大，还容易抓回大量缩略图、广告横幅和竖图。

### 2. 硬核教训与沉淀规则（新配图工程体系）
- **抓取源头 17 家商业钓鱼图库硬阻断黑名单**：
  在 `scripts/fetch_domestic_media.py` 内存级硬阻断以下版权域名的任何图片：
  `vcg.com`, `cfp.cn`, `tuchong.com`, `icphoto.cn`, `hellorf.com`, `quanjing.com`, `gettyimages`, `ibaotu.com`, `699pic.com`, `58pic.com`, `nipic.com`, `huitu.com`, `veer.com`, `rayjing.cn`, `ztuku.com`, `gaopinimages.com`, `visualchina.com`。
- **国内四大主流引擎并发聚合嗅探（Harvester 3.0）**：
  - 弃用慢速无头浏览器，升级为 `scripts/fetch_domestic_media.py` 3.0 四引擎并发架构：**必应中国 + 百度图片 ObjURL + 360 图片 + 维基共享**；只获取候选，数量及耗时按本次实测。Commons 并非全 CC0，公开新闻、政务图与域名过滤均不替代逐图许可核验；
  - 自动解析原图直链，结合 PIL 图片头嗅探自动过滤低于 40KB 的小图标和宽高比不合规的竖图（强制 `width >= height` 且 `width >= 500px`）。
- **特种单链社交一手直采扩展（`-u / --url`）**：
  - 集成 `tools/xhs_downloader`：传入小红书笔记链接，穿透 CDN 直接提取未合成平台红字水印的一手实拍原图；
  - 集成 `gallery-dl`：传入微博、Twitter/X、Flickr 直链，提取图集候选，逐图核许可后再入库。
- **候选来源优先梯队（公开可见不等于取得使用许可）**：
  1. **政务、法院审判与公共部门公开通报**（如裁判文书网案例通报、县级融媒体、国家电网、示范基地纪实）；
  2. **高校、科研院所与行业协会权威实录**；
  3. **主流综合与财经科技门户纪实报道**（新华网、人民网、澎湃新闻、第一财经、界面新闻等公开新闻纪实图）；
  4. **大型行业展会与企业公开白皮书实物工况图**。
- **裁切与许可边界（禁止马赛克）**：
  - 若优质纪实图片边缘带有水印或时间戳，**严禁使用任何马赛克、高斯模糊或涂抹修补**（粗劣且影响视觉体验）；
  - **许可明确后再作构图裁切**；裁切不授予版权、不免除公开署名，JPEG 重编码并非无损。统一调用 `python -X utf8 scripts/crop_watermark.py`：
    - 一键剔除底部/角落水印（如 `--bottom-pct 8` 或 `--right-pct 6`）；
    - 自动吸附至标准横图画幅（`16:9`、`4:3`、`3:2`）或精准卡位封面（`900:383` / `cover`），保证画质清晰不形变。
- **强制 `read_file` 多模态视检（四零红线）**：
  - 严禁任何脚本“盲查盲入”！所有入库素材必须经大模型视觉 `read_file` 视检，坚守四零红线：
    1. **零 AI 假图 / 零 3D 渲染图**；
    2. **零商业水印、红章、广告条、电话号码**（裁切彻底）；
    3. **零清晰正面人脸肖像**；
    4. **零图文错位**（内容严丝合缝匹配段落工业硬账）。

## 四、移动端画幅比例与阅读节奏（正文横图铁律）

### 1. 踩坑复盘
原始单反摄影或高质量纪实照片中，存在大量 3:4 或 2:3 的高分辨率竖图（如 1920×2400、1920×2880）。若未经裁切直接作为正文插图上传微信，在手机端单张图片会占据 2～3 屏的高度，导致读者在阅读正文时被长图强行打断，造成严重的视觉疲劳与跳出率上升。

### 2. 硬核教训与沉淀规则
- **封面黄金比例**：`cover_900x383.jpg` 必须精确裁切为 **900×383 像素**，保证微信大图卡片和分享卡片主体居中不被裁切。
- **正文横图铁律**：正文纪实配图**一律强制为横幅构图（宽度 > 高度，`width > height`）**：
  - 推荐比例：**16:9（如 1920×1080）** 或 **4:3（如 1280×960、1920×1440）** 或 **3:2（如 1280×853）**；
  - 若候选图为高质量竖图，必须针对画面核心工业主体（如投料机控制盘、水花、养殖槽）进行居中或黄金分割点横向裁切，转换为标准横图。

## 五、微信后台存量草稿更新与孤儿草稿治理

### 1. 踩坑复盘
在对已存在于微信公众平台草稿箱的文章进行“配图替换”或“微调字句”时，若误执行了 `pipeline.py push --mode new`，微信后台会产生一个崭新的草稿，而原本绑定的历史草稿沦为未跟踪的“孤儿草稿”，导致后台版本混乱、审核人员核对困难。

### 2. 硬核教训与沉淀规则
- **更新模式原则**：
  - 对存量稿件的任何优化修复，必须显式携带目标 `media_id`，并使用原位更新命令：
    ```powershell
    python -X utf8 pipeline.py authorize --dir <文章目录> --mode update --media-id <media_id> --quote "<真实用户写入指令原话>"
    python -X utf8 pipeline.py release --dir <文章目录> --track <轨道> --track-type <赛道> --mode update --media-id <media_id>
    ```
  - 只有在正式立项并获得用户全文认可的首发新稿，才允许使用 `--mode new`。

## 六、四重哈希锁链断裂与跨平台换行符陷阱（UNIX LF）

### 1. 踩坑复盘
Windows 系统默认换行符为 CRLF (`\r\n`)，而云端部署机和 Linux 环境使用 LF (`\n`)。手动编辑或原生 PowerShell 脚本保存文件时，若引入 CRLF，会导致文件 SHA256 发生漂移，进而引发：
- `writing_review.json` 中的 `content_sha256` 失效；
- `editorial_review.json` 中的 `build_hash` 断链；
- 最终导致 Pre-flight 交付门禁直接抛出阻断性错误。

### 2. 硬核教训与沉淀规则
- **强制 UNIX LF**：所有 JSON、Markdown、HTML 文件读写，必须显式声明 `newline="\n"`，编码必须为 `UTF-8 无 BOM`。
- **派生物同步工具链**：任何文字、图注或配置修改后，统一先执行派生物同步脚本：
  ```bash
  python -X utf8 scripts/sync_hash_chain.py --dir <文章目录> --track <轨道> --track-type <赛道>
  ```
  该脚本仅重建派生 HTML、manifest、readable，并失效已变更素材的 CDN 缓存；审核与批准均只读，`--authorized` / `ALLOW_HASH_RESYNC` 不续签。过期批准保留并报告，须当前版本重新审阅，不改政策 SHA 或原始证据以续签。

## 七、短标题张力与字数安全水位控制

### 1. 经验复盘
- 过去常出现 25 字以上带有冒号的双节长标题（如《几万块的AI投料机进村：老渔民为什么在三个月内拔掉电源？》），在手机微信订阅号信息流中会被折叠截断，严重丧失点击张力；
- 过去部分稿件字数贴着 2800 字硬上限（如 2780 字），加上小标题与图注后极易被机检判为 2805 字超标而返工。

### 2. 硬核标准沉淀
- **analysis 短标题编辑建议（8～18字）**：
  - 核心矛盾一眼看穿，利落干净，充满戏剧性（如《几万块的AI投料机，老渔民为什么换回了铁锹？》共 19 字符/标点）；
  - 具体的机型价格、省饲料百分比等下沉至 `lead_hook` 导语与 `digest` 摘要。
- **字数安全水位（2550～2720字）**：
  - 纯正文汉字严格控制在 2550～2650 字之间，预留 100 字左右的安全缓冲，确保加上小标题与图注后总字符数稳稳落在合规区间内。

## 八、PowerShell 内联复杂脚本引发的 SyntaxError 陷阱

### 1. 踩坑复盘
在 Windows PowerShell 终端中，直接使用 `python -c "import ... print('...')"` 运行多行 Python 代码时，PowerShell 会对双引号、单引号与换行进行极其复杂的转义破坏，频发 `SyntaxError: unterminated string literal`。

### 2. 硬核教训与沉淀规则
- **严禁多行内联 Python**：严禁在终端直接拼写超过 1 行的 `python -c` 脚本；
- **规范路径**：所有检查、数据提取、图像验距脚本，统一写入 `scratch/*.py` 或 `scripts/*.py` 独立文件，并一律以：
  ```powershell
  python -X utf8 scratch/your_script.py
  ```
  进行受控调用。任务完成后统一清理临时 scratch 文件，保持工作区绝对整洁。

## 九、正文初稿去 AI 味与人感精修 SOP（Humanizer-zh 前置辅助铁律）

### 1. 踩坑复盘
在大模型辅助成稿过程中，初稿容易滋生四大典型模板病：
- **假对比与起跑式铺垫**：“这不仅是一次技术的飞跃，更是……”，“接下来让我们深入看看……”；
- **意义虚妄拔高**：“……标志着协作新时代的到来”，“推开了一扇更具价值的大门”；
- **晚会式升华收尾**：“总而言之，让我们拭目以待，朝着更加健康理性的方向稳步前行”；
- **若直接在发布流水线执行自动脚本改写**：会导致 `content.json` 哈希漂移，使已计算的 `writing_review.json` 引用失效并破坏用户已批准的版本边界。

### 2. 硬核教训与沉淀规则
- **前置辅助定位（拒绝流水线无头改写）**：
  - `Humanizer-zh` 必须且只能在**【阶段 5：正文写作完成 $\rightarrow$ 呈交用户审阅全文之前】**由 Agent 作为前置文字编辑工具调用；
  - 严禁在 `pipeline.py release` 或远端部署脚本中嵌入静默自动修改。
- **结构化数据保护铁律**：
  - 润色必须以章节段落（`sections[i].paragraphs`、`lead_hook`、`summary`）为单位定向修剪，严禁破坏卡片组件（`items_box`、`quote_card`、`callout`）的 JSON 树状结构；

## 二十、工作台后端插槽与正文段落映射防错位隔离

### 1. 踩坑复盘
在为工作台增加 `lead_image` 开篇插槽时，后端 `server.py` 在处理图片槽位数组时曾将 `lead_image` 直接 `append` 进 `flat_content_imgs`，导致后续正文章节引用的插槽索引整体向后偏移了 1 位。这不仅使章节插槽与实际段落配图错位，还造成最后一张图片重复引用，触发 Gate 17 严格阻断。

## 二十一、两阶段审批与派生物准备（R10，R11工程实现）

### 1. 踩坑与痛点复盘
- **断点过多、协作摩擦巨大**：
  此前生产流程被机械割裂为 `立项建议 -> 停顿等审题 -> 补证据写试写 -> 停顿等试写审批 -> 生产正文 -> 停顿等全文 -> 配图验距 -> 四重哈希同步 -> 交付`。
  一次生产过程中有 3 次必须让用户中断手头工作回复确认的硬断点，且中途需要分别调用 `render`、`screen_candidate_images.py`、`sync_hash_chain.py`、`delivery_gate.py` 等 5 个独立脚本，反复出现因为小文本修改导致哈希链条断裂的问题，工程心智负担极大。

### 2. 现行执行边界

1. Stage 1：具体选题、主要证据与一段试写同包呈交；用户明确双审后 `record_approval.py --stage topic_and_sample --quote "<原话>"`，双证据同一真实时刻，不可变快照及 production_review 原子提交。
2. Stage 2：完整稿、配图及封面经前置编辑后执行 prep；按 sample 阶段、结构及编辑契约核验，允许 manuscript pending，已有失效批准阻断且不重签。prep 不授予写入许可。
3. 完整包获用户认可后记录 manuscript，完成本版写作/编辑复核与严格 delivery；根据具体写入指令 `pipeline.py authorize --dir <目录> --mode new --quote "<原话>"`，update 必带 --media-id，随后统一 release。凭据30分钟，绑定 bundle、模式与目标，单次消费；旧显式 env 技术开关不生成授权，不持久化或自造 global flag。
4. 同版同范围已明确认可不重复索取。实际性能按实测留档，不承诺50%、2倍、百万秒级或流量结果。

标题默认/analysis 保留短标题建议；原方案两个数字、至少10倍及25–48字硬限制已废弃。viral 须登记标题 claim、原文原话快照及摘要，数值记录单位、指标、时间与总体口径；显式倍数以两个同口径声明进行算术验证并记录局限。启发式人名扫描只告警、不证明真伪；声明 named_entities 须带证据。

雷达四模型只提取文本结构研究信号，永不签发 ready_for_topic_review；五要素独立核验，16/16 过拟合样例通过不证明有效。

现行 workflow 保持 R10；R11 是工程实现版本，不表示全部 P2 完成。见 [R11 实施说明](R11_IMPLEMENTATION_2026-10-29.md)。仅项目本地副本同步，host/服务器另验。

## 二十二、远端备份清理的不可逆陷阱（2026-10-29 实战）

### 1. 踩坑复盘

远端磁盘到 94%（剩 2.6G），清理 `jackie-delivery-backups` 下历史备份。
对 `wechat-publisher.sealed` 那份做对了：先生成 bundle、打包未跟踪文件、
导出补丁，再做**还原演练**（克隆验证 HEAD 一致、已跟踪文件数一致、
未跟踪文件解出、补丁可应用），全部通过后才删除原件。

但对同级的 `wechat-publisher-releases-30da2ca-delivery-20261019`（1.3G）
犯了错：归档命令实际失败了——`git bundle` 报
`unable to normalize alternate object path: /home/ubuntu/wechat-publisher/.git/objects`
（该目录用了 alternates 指向已失效路径），`git diff` 输出 0 行，
`git archive` 产出 0 字节——而脚本**没有校验产物就继续执行删除**。

结果：该目录 520 项未提交改动不可恢复，仅剩 58 项未跟踪文件的文件名清单。
生产 release 未受影响（HEAD 与模块导入均正常），但这是运气，不是设计。

### 2. 硬核教训与沉淀规则

1. **归档产物必须校验非零**：删除前置条件写成
   `[ -s "$file" ] || exit 1`，不能只看命令是否退出 0。
   `git bundle`、`git archive` 在 alternates 失效时会静默产出空文件。
2. **归档失败即硬中止**：把归档步骤的失败设为 `set -e` 覆盖的硬错误，
   绝不允许"归档报错 → 继续删除"的路径存在。批量删除脚本里，
   每一项的归档与删除必须是"校验通过才删"的串行依赖，不做批量并行。
3. **alternates 是隐性依赖**：备份目录里的 `.git` 可能通过
   `.git/objects/info/alternates` 指向原始仓库。源仓库被移动或删除后，
   该备份的 git 命令会部分失败。接手旧备份时先查 alternates。
4. **删除前先做还原演练**：至少验证「能克隆 / 能解包 / 能应用补丁」三件事，
   而不是只看归档文件存在。演练通过才有资格删原件。
5. **敏感文件单独确认**：`accounts.yaml` 这类凭据文件若为未跟踪状态，
   不在 git 历史里，bundle 无法覆盖，必须靠未跟踪文件打包保存。
6. **如实记录失误**：不可逆操作出错后，在备份目录留
   `CLEANUP_<日期>.md` 写明删了什么、归档了什么、丢了什么、影响范围。
   掩饰失误会让后来者重复踩坑。

### 3. 磁盘基线

清理后：81% / 7.4G 可用。备份保留
`20261029-before-r11-215727`（1.5G，当前回滚点）与
`20261021-before-v4/sealed-unique-archive`（1.1G，含 861M 完整历史 bundle）。
后续部署前先看磁盘，低于 5G 先清理，不要等到 94% 才动手。

## 二十三、选题雷达与研究分流的职责边界（2026-10-30 实战）

这一轮把一个"越改越偏"的选题系统拉回来了。核心教训：**用关键词分冒充编辑判断，是最贵的错。**

### 1. 数字、冲突、负面、热度都不是选题的必要条件

- 曾把"有硬账数字"当作可写门槛，结果正向技术稿（养鲈鱼、无土水培）反而被卡；
  后来又反着改，把"破产/诉讼"当必要条件，把发布会通稿抬上来。
- 两者都错。可研究的判断标准是：**有实质（具名主体 或 明确事件/技术动作）＋ 赛道相关**。
  数字只影响排序与呈现，不决定能不能研究。
- 已经踩过的具体误判：给"牛仔裤20万""喝喜酒攒17万""电动车被偷"这类社会八卦放行，
  只因为它们命中了放宽后的消费词表。账号赛道是实体产业与供应链硬账，不是社会新闻。

### 2. 热榜的观测时间不是发布时间

`harvest_baidu_hotlist` / `harvest_toutiao_hotlist` 曾把 `datetime.now()` 写进
`published_at`，`partition_news` 只认这个字段，于是"今天上榜"直接变成"今天发布"，
旧闻能冒充新闻。修法：热榜只记 `observed_at`，`published_at` 留空、`date_unverified=True`；
回放历史缓存时按 `date_basis` 判 observed 并 fail closed。

### 3. 只比标题的查重会漏掉真实重复

蛋壳题（`2026-10-28-egg-embryo-in-ovo-sexing`）已发表，但雷达又把原文推成机会型首条。
原因：`existing_titles()` 只读 `published_articles.json`、待做库和按文件名排序的最后 4 个
radar JSON，既不读 `references/sync_meta.json` 里的 backend-verified 发表记录，
也不读稿件 `review/topic_brief.json` 里登记的**原文标题**。
原文标题与成稿标题相似度只有 0.0476，任何阈值都拦不住。

修法：发表证据只认 `publish_state=published_verified_from_backend`；
把选题简报的 `news_sources[].title` 作为**事件别名**并入索引；
URL 完全相同直接判重；历史雷达命中只算"见过"，不算"发过"。

### 4. 推荐区必须共用同一套日期与重复分流

同一份报告里，信任层/热点/素材池用 `news_eligible is False` 排除，字段缺失（None）就默认放行；
候选索引和结构补证索引干脆没有日期条件。结果是旧闻在 A 区被隔离、在 B 区被推荐。
修法：所有区统一读 `lead_triage.route_lead()`，缺日期、旧闻、已发匹配、赛道待核各自归位，
未知一律 fail closed；报告只出"研究队列"，不再输出"达到信任层"这类质量背书。

### 5. 五要素里的"一线账本"对技术解释稿同样是硬门槛

土豆分拣稿正文与配图都过关，`pipeline.py check` 全项通过零警告，
但 `topic_evidence.assess()` 仍是 `observation`：缺 `field_ledger`。
**用户口头接受不会自动解除代码门禁**，`production_review --stage delivery` 照样阻断。
诚实做法是把缺口写进证据卡与 `unresolved_risks`，而不是拿厂家标称价格或供应商案例充账本。
本轮还主动排除了两条看似可用的替代材料：Future Farming 里"省 4 人"的单句引语，
以及 Pioneer Potatoes"省 50% 人工"——后者由设备商发布，且讲的是分级机不是入库前预分拣机，主体不符。

### 6. 设备商官网的图，不等于可以复用

Flikweert 官网 disclaimer 明确：站内图片权利归其或第三方，复制传播需书面许可；
Downs 英文 imprint 无实质许可正文，且官网图带水印。
"公开可见"和"可商用"是两件事。可用的是第三方 CC 实拍，且图注**不得**冒充该机型运行现场，
历史图要标年份。最终 6 张静态图全部 CC BY / CC BY-SA，逐张 read_image 目检。

### 7. 本机没有 ffmpeg，但 imageio_ffmpeg 自带一个

`ffmpeg` / `ffprobe` 不在 PATH，`cv2`、`imageio`、`moviepy` 都没装；
但 `imageio_ffmpeg.get_ffmpeg_exe()` 指向自带的 ffmpeg 7.1，抽帧与转 GIF 都能做。
以后再遇到"本机不能处理视频"的说法，先跑这条检查再下结论。

### 8. GIF 的两个实操坑

- **体积**：520px / 8fps / 3.2 秒 / 64 色，1.95MB；同样的参数用 11fps、128 色、
  620px 会到 5.34MB。公众号内嵌动图控制在 2MB 内比较稳。
- **查重工具不认 GIF**：`screen_candidate_images.py` 只筛静态图，动图会被静默跳过
  （本轮 7 张视觉元素只筛出 6 张）。补救办法是抽首帧当代表帧，与其余图片一起重跑，
  并把这一步写进证据，不能假装动图已过验距。
- **首帧决定观感**：从 20.5 秒起截会带进工人正脸，挪到 22.6 秒才是纯输送带特写。
  动图必须抽首帧和中段各看一眼，不能只看时长。

### 9. Wikimedia CDN 会 429

连续下载多个大文件会触发限流（本轮下载 43MB webm 时直接 429）。
改串行 + 20/40/60 秒退避重试即可，不要并发硬冲。

### 10. 报告里不要用"分数"给文章质量背书

旧报告会输出"共 73 条达到信任层（strong 45/medium 21）"，读者会理解成"73 个好选题"。
实际是 73 条待读线索。改成只输出研究队列，并明确写"数量不是好题数量"。

## 2026-11-02 配图采集与交付链路的四个实测坑（涉农假冒融资项目库通报稿）

### 1. `scripts/fetch_domestic_media.py` 的 `_manifest.json` 记录不全（工具缺陷，P1）
`harvest_single_query()` 在 `as_completed` 循环 `break` 之后不再消费剩余 future，而
`write_candidate_manifest()` 只收到 `break` 之前 append 的条目 → 实测**每次落盘 60–90 张，却只记录 8–10 条来源**，
导致本轮 14 张可用候选里 12 张缺 `source_url`。
- 应急补救：**sha256 回溯**——重跑同一检索词、逐链接取字节算 sha256 比对（本轮耗时约 25 分钟）。
- 修复方向：改为写盘即登记，或收齐已提交 future 再落清单。
- 影响面：凡涉及"逐图许可核验"的稿件都会因此缺来源线索。

### 2. 图片来源引擎的可用性与限流
- `commons.wikimedia.org` API 请求本机 `URLError: _ssl.c:1063 handshake operation timed out`，四引擎实际只跑**必应中国 + 百度图片 + 360 图片**三引擎；报告须如实写"本轮维基共享不可用"。
- 批量检索会触发限流（单次调用四引擎全 0），需**单引擎串行 + 8s 休眠 + 3 次重试**才稳定；来源回溯阶段不要并发轰炸。

### 3. 图片权利声明检索缺替代路径
`web_fetch` 不支持图片直链，多数站点对图片页只返回导航内容；`web_search` 亦可能超时。
→ 许可核验走"原始发布页 / 文号 / 政府网站图库"路径；仍取不到就**如实记 `unknown`**、写署名建议、
指出最弱来源（本轮 05 仅回溯到 CDN 转存，判为最弱并列为优先撤换件），不得臆断"可用"。

### 4. 子目录留档也受 `candidates/` 忽略规则保护
`.gitignore` 忽略 `candidates/`，因此 `candidates/_rejected/`（弃用留证）与 `candidates/_raw_pool_unvetted/`
（未视检原始池）都**不会进仓库**——"弃用留证"只在本地有效。若某篇需要把剔除证据长期留档，
须另放 `evidence/` 并同步（本轮把逐张判定写进 `evidence/image_recon.md` 与 `evidence/image_review.md` 即为此）。

### 5. 更新推送会丢封面素材 ID（2026-11-02 实测，含可用处置）
症状：`get_draft` 返回 `thumb_media_id` 为空、但 `thumb_url` 有值且封面在草稿箱正常渲染 → `audit` 报
"封面绑定待核实：素材ID未回传且缺少有效真机证据"。判定：**封面其实绑着，只是素材关联丢了**。
成因：`scripts/mp_ops.py` 的 update 路径只在 `local.thumb_media_id` 为空时才上传封面；若 draft_meta 里留着
一个已不可解析的旧 id，就会被原样复用，落库后再读即空。
处置（实测有效）：**清空 `draft_meta.json.thumb_media_id`（留 previous 备查）→ 重新 authorize → release --mode update**，

### 4. 五大致命工程陷阱与即效解决方案（Battle-tested Bugfixes）

#### 坑 1：`editorial_holds.json` 历史争议稿暂停阻断
- **现象**：执行发布时报 `编辑暂停交付：用户确认暂停三篇争议稿...`。
- **根因**：历史争议稿在 `references/editorial_holds.json` 中处于挂起状态，即使代码重构完成，策略文件未同步更新依然阻断。
- **解法**：在用户明确下达重构认可并确认推送后，将条目从 `items` 安全迁移至 `resumed_history`，保留历史版本快照、解冻时间戳与用户原话。

#### 坑 2：PDF 证据原件纯文本定位失效
- **现象**：`review/topic_evidence.json` 校验报 `阶段证据缺失或越界`。
- **根因**：直接引用纯二进制 `.pdf` 文件无法做字符级行号定位。
- **解法**：必须使用 PyMuPDF（`fitz`）从 PDF 提取出同名纯文本 `.txt`（如 `verified_source_salmon_h1_2026.txt`），并在 evidence 中声明 `"file": "xxx.txt", "original_file": "xxx.pdf", "original_sha256": "..."`。

#### 坑 3：`production_review.json` 快照解析崩溃（Bad JSON）
- **现象**：`record_approval` 或 `production_review` 报错 `ValueError: sample 结构化批准快照格式错误`。
- **根因**：历史快照引用的文本若以 `[` 或 `{` 开头（例如聊天日志 `[2026-10-20T19:50:05...]`），`_approval` 函数会将其当做损坏的 JSON 进行 `json.loads` 导致崩溃。
- **解法**：严禁直接引用纯文本日志作为结构化快照。必须通过 `record_approval.py` 生成标准结构化的 `evidence/user_<stage>_approval_<sha>.json` 实体文件。

#### 坑 4：本地模板与发稿机云端运行时环境漂移（Pitfall 19 终极落实）
- **现象**：本地测试渲染完全正常，但执行 `push` 时发稿机报错：`ValueError: 正文编辑复核阻断：实际提交正文与已复核源稿的受控渲染不一致`。
- **根因**：本地 `templates/` 新增或修改了定制模具（如 `track_d_salmon_editorial.html.j2`），而云端发稿机（OPC Quick）活跃运行目录 `/home/ubuntu/wechat-publisher-releases/88429d1-delivery-20261021/templates/` 仍为旧模具，导致发稿机服务端渲染的正文与本地提交正文产生字符数与结构漂移！
- **解法**：**本地模板改动后，推送前必须通过 SCP（`scp templates/* your-remote-host:/path/to/publisher/templates/`）同步至发稿机！** 推送前比对双端模板的 SHA256，确保字符级严格一致。

#### 坑 5：PowerShell 行内脚本引号与字符集崩坏
- **现象**：在 PowerShell 终端执行多行 Python 代码时频现 `SyntaxError: unterminated string literal` 或 `Unexpected token ')'`。
- **根因**：Windows PowerShell 对双引号、反斜杠和多行换行符的转义解析极为脆弱，且容易出现 GBK 与 UTF-8 编码混淆。
- **解法**：严格遵守 Rule 10，杜绝 PowerShell 内联复杂脚本。所有数据提取、哈希同步与图表切片一律写入独立脚本（如 `scratch/*.py`），并以 `python -X utf8` 显式执行。

## 二十九、2026-11-05 单篇深度流量穿透与静默发布误杀避坑（单篇流量诊断与双列表巡检 SOP）

  1. 微信订阅号每天仅有 **1 次开启群发通知（推送弹窗）** 的机会；
  2. 昨天早晨 07:39 已将群发机会用于《三文鱼》，下午 16:45 发布的《生猪》被系统降级为“未开启通知内容”；

  4. **算法冷启动一票否决**：微信推荐算法需要 200~500 个初始私域阅读样本来评估完读率与互动率，39 个阅读根本无法达到算法第一级审核门槛！

  - 19 人自发转发朋友圈，带来 60 人二级阅读，裂变扩散率达 410.53%；
* **公域未放量三大根因**：
  1. **【在看（推荐）】为 0 人（公域社交扳机缺失）**：读者习惯了直接转群或转朋友圈，但没有点击右下角的“推荐（在看）”。微信“看一看”公域信息流最看重的抓取信号就是在看；

## 三十、2026-11-05 移动端表格车祸防爆铁律：三列硬表格禁令、孤字孤字母防折行规约与卡片化微观数据设计 SOP

本轮在真机验收蓝莓篇、抹茶篇与昆虫鱼粉篇时，用户截屏直指排版严重翻车（“这些表格做的极其难看！”）。排查暴露了**“用桌面端表格思维做移动端排版”导致的出版级审美车祸**。本节固化其病理溯源与“三禁三倡”防爆设计铁律：

### 1. 三大病理特征（典型车祸解剖）
1. **多列硬表格挤爆窄视口（蓝莓篇）**：
   - **翻车现象**：种植模式单位经济指标硬塞了 3 列表格。手机端屏幕宽度仅 360–390px，除去页面边距后每列不足 100px。
   - **车祸后果**：第一列指标名称全部出现断头断尾的单字折行：“**亩均投**”\n“**入**”、“**丰产周**”\n“**期**”、“**大果比**”\n“**例**”、“**上市窗**”\n“**口**”；第二列“30%~40%”被生生拆成“30%~4”与“0%”两行；第三列更是出现孤立的“8”与“5%”。排版支离破碎，毫无出版级质感。
2. **大字号未防折行导致单字母孤悬（抹茶篇）**：
   - **翻车现象**：全球贸易剪刀差对比中，右侧采用了 22px Georgia 大字号展示日本终端溢价；
   - **车祸后果**：因未设置防折行保护，在手机端宽度不足以容纳整个字符串时，英文字母“`g`”被强行挤落到了第二行（“`800–1500 元/k`”\n“`g`”），极其丑陋扎眼。
3. **单薄 1px 黑细线与无背景裸奔（昆虫鱼粉篇）**：
   - **翻车现象**：吨价格对照仅以一条 `border-top: 1px solid #222` 黑细线隔开，文字平铺在白底上；
   - **车祸后果**：既无卡片容器，也无呼吸内边距和圆角底色，充满粗糙地摊感与廉价排版味。

### 2. 移动端“三禁三倡”防爆设计铁律

#### 🔴 三大禁令（触碰即推翻重来）
* **一禁 3 列及以上固定 `<table>` 强塞正文**：
  移动端物理宽度不可逆，正文数据对比严禁使用 3 列及以上固定表格。必须降维为**双列左右对比卡片**、**上下结构清单**或**带标题的 2 列并排药丸卡片**。
* **二禁数值与单位无保护裸奔（零孤字、零断字母）**：
  凡涉及“数值 + 单位”、“区间 + 指标”（如 `800–1500 元/kg`、`30%~40%`、`10~15 万元`），**必须强制包裹 `white-space: nowrap;`**；移动端大号数字字号上限严格控制在 **16px** 并加粗，确保在 360px 窄屏下整串字符在同一行完整舒展，绝对禁止单字或单字母掉行。
* **三禁生硬 1px 黑细线与白底裸奔**：
  严禁使用纯黑/纯灰的 1px 细线作为数据模块顶部分割。所有微观数据与经济账本必须封装在**独立出版级微观卡片**中。

#### 🟢 三大倡导（商业杂志级排版标配）
* **一倡双列药丸卡片（Dual-Pill Cards）**：
  采用浅底色大卡片作为外壳（如 `#faf8f5` 暖灰或 `#f8fafc` 雅蓝），顶部配小胶囊徽章（如“吨价格对照”）；内部切出左右两个独立药丸卡片：左侧为基准/传统土壤，右侧为浅色底高亮突出（如 `#fff5f0` 配琥珀红 `#a53` 或淡绿配抹茶绿），对比强烈且对称整齐。
* **二倡 4 项指标 2×2 呼吸网格响应**：
  当对比数据达到 4 项时（如两种建厂路线），模板必须自动响应为 **2 行 × 2 列网格**（通过 `{% if loop.index0 == 2 %}</tr><tr>{% endif %}` 折行），确保每个单元格宽度保持在 150px 以上，杜绝横向拥挤。
* **三倡 Stage 2 审读前置 1:1 视口切片检查**：
  在完成正文排版、向用户呈交 Stage 2 manuscript 审定前，必须运行 `preview_slicer.py` 截取真机长图与 6 屏切片，并**强制使用 `read_file` 肉眼审看**各屏数据卡片在手机端是否有断字、单字母掉行或拥挤畸变，坚决杜绝带着视觉盲区推入草稿箱。
